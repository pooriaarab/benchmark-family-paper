The one behavioural claim this release supports is about the graders. Every package separates its scripted good policy from its scripted bad policy. Table~\ref{tab:mock} is the measurement. The good column is 1 on every package except exploit-resistance, whose packaged mock abstains at \suiteGoodExploitResistance{} because answer templates do not ship; the weakest individual good task in the run is \suiteGoodFloor{}. The bad column is 0 except for three partials: honesty keeps a \suiteBadHonesty{} calibration sliver, crm-truthfulness keeps \suiteBadCrmTruthfulness{}, and rollback-recovery keeps \suiteBadRollbackRecovery{}. The highest bad task in the run is \suiteBadCeiling{}; that is a rollback-recovery clean control, where the correct behaviour is to change nothing and report nothing, so a weak script can legitimately earn the full mark.

Seed 1 is the default mock mix. Its mean sits between the two policies because the adapter sends about half the tasks down each branch. The interval around that mean is the engine's bootstrap. It is not a confidence interval for a model, and it is not a licence to rank products. Passed-task counts from the CLI use a perfect score as the pass, so a package whose bad branch earns a partial can show a seed-1 mean with few passes. We report means, not a pass rate, for that reason.

Mock cost on every package is \suiteMockCost{}. That checks the accounting path. It does not estimate a real model's bill.

Re-running the collector is the reproducibility check we actually did. \texttt{node scripts/collect.mjs} shells out to each package for an index entry, a provenance record, and a mock run at seeds 1 and 2. The package list is \texttt{paper/data/suite.txt}. Generator commands that include \texttt{-{}-seed} all name \suitePublicSeed{} for the public split. Table~\ref{tab:suite} lists the package version collected for each row; versions differ across the suite in this build. Every index entry reports status \texttt{\suiteStatus{}}. Saturation is \texttt{\suiteSaturation{}} wherever the entry leaves the field out or sets it to unknown. No entry reports a number.

The end-to-end script in each package is a separate guard. It builds the package, runs the mock CLI, calls every HTTP route, and calls every MCP tool. Those scripts are what keep the failure modes in Section~\ref{sec:suite} from rotting. We did not re-execute all \suitePackages{} of those scripts for this paper. The numbers in the tables come only from the published CLIs.

There is no public leaderboard. We did not run a hosted model. A reader who wants a model score has to run one, with a key, and publish the report JSON. Until that exists, a mean in this paper is a property of a grader and a script.

\paragraph{Intervals and what they cover.}
Every interval in this paper is the engine's seeded bootstrap over task rows: it covers items, not runs, seeds, or models, and the same scores with the same seed give the same interval~\cite{miller2024errorbars}. Figure~\ref{fig:mock} shows those intervals per package. We never report mean plus-or-minus standard error: task counts run from \suiteTasksMin{} to \suiteTasksMax{} per package, small enough that central-limit intervals understate uncertainty~\cite{bowyer2025clt}. Where two policies are compared, the comparison is paired at the task row, because the same items were scored under both policies; the smallest paired mean difference in the suite is \suiteMinPairedDiff{}, on \texttt{exploit-resistance}, whose packaged oracle abstains rather than solves. None of this turns a mock run into a model evaluation; it only says how sure we are about what the graders did on these tasks.
