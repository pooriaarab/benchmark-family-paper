\section{Review-record statistics}
\label{app:reviewstats}

\paragraph{Council coverage.}
The council workflow was the other review layer. On the pull-request record, the \texttt{claude} account it posts under authored \councilReviews{} reviews on \councilPrsReviewed{} of the \buildersPrs{} pull requests in the \suitePackages{} repositories: \councilApproved{} approvals, \councilCommented{} comment reviews, and \councilChanges{} change requests (\texttt{paper/data/council.csv}, rebuilt by \texttt{scripts/council.mjs} from the GitHub API on 2026-10-16). Coverage was not total: of the \councilMergedFeature{} merged feature pull requests, \councilMergedNoReview{} carry no council review, \councilMergedNoApproval{} were reviewed but never approved, and \councilMergedCheckFail{} merged while the council check showed a failure on the head commit. Only \councilMergedApproved{} of the \councilMergedFeature{} merged feature pull requests carry a council approval.

\paragraph{Severity method.}
The council read the diff and often had findings: \councilSeverityReviews{} of its reviews by the regex raise an open Critical or Major item, many of them about process, on at least \councilSeverityPrs{} pull requests (a regex estimate over review bodies, hand-checked on a \councilSampleSize{}-review stride sample, every k-th entry of the sorted list, where all \councilSampleSize{} agreed with the regex flag; a full read of the unflagged reviews finds \councilSeverityRegexMissed{} reviews the regex missed, while the \councilSeverityRegexFalsePositives{} false positive on record is a lower bound because the flagged reviews were not all re-read, so the real count is about \councilSeverityReviewsRead{} reviews on about \councilSeverityPrsRead{} pull requests; method in \texttt{paper/data/README.md}). On sycophancy's pull request 20 the council flagged the published hidden seed as an open Major, and the builder removed it before the request was approved and merged. What the council did not do is probe: its reviews read the diff and sometimes push fixes, but they do not run attack policies against the built package.

\paragraph{Approvals behind defects.}
Pelican's pull request 4 replaced string equality with the structural SVG scanner and earned a council approval written by the chair alone, both other members having timed out; issue 8 in the same repository then records that the grader discarded the task it was scoring, so one memorised SVG scored 1.0 on every public and hidden task. Sycophancy's pull request 20 is the second case: it was approved at commit \texttt{4ffa15c} while its generator still defaulted hidden plans into \texttt{data/}, a directory the npm package ships, and the docs claimed the courtesy check caught slurs; its pattern held six insult terms and no slurs. The probing review's released fix brief records both defects, and they were fixed in commit \texttt{7a60894} after the approval; the merged head \texttt{25c8d27} sits three commits after the approved one, and the council never re-reviewed the request. Table~\ref{tab:approvaldefects} lists both records. Those are \approvalDefectCases{} documented cases among \councilMergedApproved{} approvals on \councilMergedFeature{} merged feature pull requests where an approval stood behind a defect a probing review later found.
