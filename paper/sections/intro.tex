Every package in this suite was built by an AI coding agent, and no test job failed on the last commit of any of the \councilMergedFeature{} merged feature pull requests (six of them had failed the shared \texttt{check} job on an earlier commit). The LLM council that reviewed them approved \councilMergedApproved{} of the \councilMergedFeature{} merged feature pull requests. A probing review of the built packages still found defects in all \suitePackages{} of them. The approvals were made by reading the diff; the probing review attacked the running artifact and found defects the approvals missed.

The artifact underneath the finding is small. \texttt{benchmark-core} is a shared TypeScript engine. \suitePackages{} packages sit on it, each with its own tasks and deterministic grader, published on npm and under \path{github.com/pooriaarab/benchmark-*}. One \texttt{defineBenchmark} call produces four ways to run the same task set: an SDK import, a command-line interface, an MCP server, and a fetch-style HTTP handler. A mock provider runs the whole suite offline with no key, so a second machine can check every grader without a model. Figure~\ref{fig:system} shows the shape. The directory that lists the packages is \url{https://private-repo-337e.com}.

The review record is public. All \reviewPackages{} packages needed at least one fix round, meaning one cycle of probing findings and their fixes (median \reviewRoundsMedian{}, maximum \reviewRoundsMax{}; Figure~\ref{fig:rounds}). The first \reviewWaveOne{} shipped a 0.2.0 whose changelog states that 0.1.0 scores are not comparable, a sentence the fix briefs required and the scoring changes behind it justify. At least \defectBlindStrategyCredit{} packages record a strategy that ignored the task and still earned credit. Section~\ref{sec:review} names \defectClasses{} defect classes, counts the packages each one touched, and cites the issue, pull request, or changelog line behind every cell (Table~\ref{tab:defects}, Appendix~\ref{app:locators}).

The same record holds the counter-evidence. The council workflow posted \councilReviews{} reviews on \councilPrsReviewed{} of the \buildersPrs{} pull requests in the \suitePackages{} repositories, and it raised an open Critical or Major item in at least \councilSeverityReviews{} of them, so approval-style review was not empty. Yet it approved pelican's grader pull request, and an issue in the same repository later records that one memorised SVG scored 1.0 on every task; the probing sessions found that defect by attacking the built package, where the approval had only read the diff. The defect findings came from those probing sessions; the protocol in Appendix~\ref{app:protocol} is the re-review one used to re-check fixed packages, and the protocol the first-round sessions used is not released. The claim the data supports is about the depth and the verdict of review: green checks and approvals did not find what adversarial probing found. The author configured the reviewer sessions as agent sessions given a protocol, there is no human-built control, the suite is one pipeline of \suitePackages{} packages, and no real model has been run, so this paper claims nothing about any model's ability.

Our contributions are:
\begin{enumerate}
\item the defect finding and a sourced taxonomy of \defectClasses{} classes across \suitePackages{} agent-built packages (Section~\ref{sec:review}, Table~\ref{tab:defects}, Figure~\ref{fig:defects});
\item the per-package fix-round record (Figure~\ref{fig:rounds}) and the re-review protocol the re-check sessions followed, short enough to reuse (Appendix~\ref{app:protocol});
\item the artifact: one engine, \suitePackages{} packages, four surfaces each, with provenance and a licence per task source (Sections~\ref{sec:engine} and \ref{sec:suite});
\item validity documentation per package: construct, scope, and task generation in one table (Section~\ref{sec:validity});
\item the checks we could run without a model: oracle-versus-trivial separation with seeded bootstrap intervals, and a plain account of what those checks do not show (Section~\ref{sec:validation}).
\end{enumerate}

The pelican package needs a credit up front. The prompt ``Generate an SVG of a pelican riding a bicycle'' is Simon Willison's, used since October 2024 as a quick look at whether a model can draw~\cite{willison2024pelican}. Our package turns that prompt into a structural grader and a seeded grid of variants.
