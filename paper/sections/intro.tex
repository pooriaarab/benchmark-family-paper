Agent benchmarks get expensive, brittle, or stuck. A leaderboard fills up, the items leak into training data, and a rerun needs the same closed model, the same paid tools, and a grader a second lab cannot replay. The interesting failure, a wrong refund or a weakened test or a tool call that should have been refused, disappears into one average.

This paper describes a smaller target. \texttt{benchmark-core} is a shared engine. \suitePackages{} packages sit on it, each with its own tasks and grader, published on npm and under \path{github.com/pooriaarab/benchmark-*}. The directory that lists them is \url{https://aibenchmarkindex.com}.

The packages are not a claim about which model is best. Version \suiteVersion{} ships an offline mock provider and no public leaderboard. What we can check today is narrower. The grader separates a scripted good policy from a scripted bad policy, the same seed reproduces the run, and a second person can execute the benchmark with no API key. Section~\ref{sec:validation} reports those checks. Scores on real models are future work.

One install exposes four ways to run the same tasks. A program can import the SDK. A person can use the CLI. An agent can talk to the MCP server. A Worker or a Node process can mount the HTTP handler. The benchmark author writes tasks, a grader, and provenance. The engine builds the rest.

The pelican package needs a credit up front. The prompt ``Generate an SVG of a pelican riding a bicycle'' is Simon Willison's, used since October 2024 as a quick look at whether a model can draw~\cite{willison2024pelican}. Our package turns that prompt into a structural grader and a seeded grid of variants. It does not replace the blog, and it does not rank models by how charming the bird looks.

Large agent benchmarks already exist, and we use them as prior art rather than as a leaderboard to beat. SWE-bench scores patches against real repository tests~\cite{jimenez2024swebench}. WebArena scores browser agents against site state~\cite{zhou2024webarena}. $\tau$-bench scores policy-following conversations against a database~\cite{yao2024taubench}. Those projects answer different questions. Ours is about packaging a grader so that a rerun is boring.
